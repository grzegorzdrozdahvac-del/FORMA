## Bridge additions beyond the plan
scanAll(ms), stopScan(), getState(); night data rows are [t, rr, hr, n] (n = RR count in the packet; JS applies the stale-repeat rule only to n == 1, like live mode). startNight returns {"ok":false,"error":...} on failure. Extra events: scanState, night (started/stopped), warning (lowBattery), appResumed, error, permissions.
Night CSV has "#start", "#gap", "#end" comment lines (parsed by NightStore, skipped in getNightData).

## Design decisions
- Scan is unfiltered; callback keeps devices advertising 0x180D or named WHOOP*/Polar* (with ScanFilter alone a WHOOP not advertising the UUID would be missed).
- Wake alarm and "Zakończ" action go to WakeAlarmReceiver, which calls NightService.instance.requestStop() directly, or NightStore.finalizeOrphan() when the process/service is dead (no background FGS start needed). START_STICKY restart resumes the same file (append) from Prefs.
- No dynamic receivers, so ContextCompat.registerReceiver is not needed. All PendingIntents use FLAG_IMMUTABLE.
- Night below 6 valid windows is NOT saved automatically: card offers "Zapisz mimo to" / "Odrzuć".
- Blob downloads in the web UI (export JSON/CSV buttons) will not work in WebView (no DownloadListener). Not implemented.

## Compile-risk spots (ranked)
1. BleManager: overriding deprecated BluetoothGattCallback.onCharacteristicRead/onCharacteristicChanged (2/3-arg) with @Deprecated + @Suppress; reading characteristic.value, descriptor.value setter + writeDescriptor(cccd) (deprecated API 33, still functional). Should be warnings only.
2. BleManager: many `return@post` labels inside main.post lambdas; `val dev: BluetoothDevice = try {...} catch { ...; return@post }`.
3. NightService: unqualified STOP_FOREGROUND_REMOVE and `this` inside Runnable SAM lambdas (reconnectTick); startForeground(id, n, ServiceInfo.FOREGROUND_SERVICE_TYPE_CONNECTED_DEVICE) guarded by SDK_INT >= 29.
4. FormaBridge: JSONObject.put with `x ?: JSONObject.NULL` (Any overload); @JavascriptInterface methods with Int param (scan/scanAll).
5. MainActivity: registerForActivityResult / OnBackPressedCallback rely on androidx.activity coming transitively from appcompat 1.7.0 (it does, activity 1.8.0).
6. Manifest: android:usesPermissionFlags="neverForLocation" with tools:targetApi="s" on BLUETOOTH_SCAN. neverForLocation can hide some beacons from scans; WHOOP/Polar are unaffected.
7. gradle-wrapper.jar was generated by local Gradle 8.14.3, then distributionUrl edited to 8.9 (the `wrapper` task needed network for an explicit version). The jar is only a bootstrap and works with 8.9.
8. Runtime (not compile) risks: Android 14 FGS type connectedDevice requires BLUETOOTH_CONNECT granted before startNight (checked in bridge); Samsung/Xiaomi etc. may kill the service despite battery exemption; GATT status 133 on first connect (handled as disconnect, night service retries with backoff); WHOOP allows one connection at a time.

## WHOOP Developer API (v2)
- New: WhoopClient.kt (object; HttpURLConnection only, no libraries; OAuth code flow, refresh on expiry or 401, pagination limit=25/nextToken, cycle v2 with v1 fallback, one 2 s retry on 429). FormaBridge: whoopSetCredentials(id, secret) (two empty strings wipe everything), whoopAuthorize() (ACTION_VIEW in the browser, redirect pl.forma.app://whoop-callback), whoopStatus() (never returns secret/tokens; first call after page load also carries a pending authResult for cold start from the redirect), whoopSync(sinceIso) (background Thread, result as event {type:"whoopSync", ok, data{recovery,sleep,workout,cycle}} or {ok:false, code, message}), whoopDisconnect(). Auth result event: {type:"whoopAuth", ok, code?, message?}. Error codes: config, auth, state, denied, offline, rate, http, app.
- Token exchange happens natively in MainActivity.handleWhoopIntent -> bridge.handleWhoopCallback (the code is NOT passed to JS; the secret never leaves the device side). Manifest: VIEW/BROWSABLE intent-filter scheme pl.forma.app host whoop-callback on MainActivity (already singleTask). External https links (developer.whoop.com) now open in the browser (shouldOverrideUrlLoading).
- Storage: SharedPreferences file "forma_whoop" (client_id, client_secret, tokens, state, pending_auth). allowBackup is false, so it is not backed up.
- Compile-risk spots (WHOOP): (1) WhoopClient.http: try/return/catch/throw/finally with all paths returning or throwing; (2) tokenRequest: smart cast of `json` after `if (... || json == null || ...) throw`; (3) handleCallback: Thread lambda capturing nullable vals (code/state) with smart casts after throw; (4) fetchAll: do/while using `token` declared outside; JSONArray.put(recs.opt(i)) overload resolution; (5) ensureAccess: non-local `return` inside synchronized { } lambda; (6) FormaBridge.whoopAuthorize: `val url: String = try {...} catch { return ... }`; java.time.Instant (minSdk 26 OK); (7) MainActivity: `this@MainActivity.startActivity` inside the WebViewClient object, new import android.net.Uri.
- Runtime risks: WHOOP app review/redirect URI must match exactly (add pl.forma.app://whoop-callback in the developer dashboard); some browsers ask before opening the custom scheme; v2 field names taken from the docs, unverified against live data.

## WHOOP Data Export import (CSV/ZIP) + file chooser
- Web: whoop-export.js (parser, header keyword rules, ZIP STORE/DEFLATE via DecompressionStream('deflate-raw'), merge through the existing WHOOP patch model), UI in Profil -> Konto WHOOP ("Bez konta deweloperskiego"). assets/www/index.html re-copied from forma-app.html.
- MainActivity: WebChromeClient.onShowFileChooser + registerForActivityResult(StartActivityForResult) + fileChooserParams.createIntent(); result via FileChooserParams.parseResult -> ValueCallback<Array<Uri>>. One callback call per request (null on cancel / launch failure / onDestroy). This also makes the old "Wczytaj kopię (JSON)" input work in the WebView. New imports: android.webkit.ValueCallback, android.webkit.WebChromeClient.
- Compile-risk spots: (1) `ValueCallback<Array<Uri>>?` property vs. platform type returned by parseResult (Array<(out) Uri!>!) passed to onReceiveValue; (2) override signature of onShowFileChooser with fully qualified WebChromeClient.FileChooserParams? (must keep nullable params); (3) `fileChooserLauncher` property initialiser references `fileCallback` (declared above it) inside a lambda; (4) smart cast of filePathCallback after the null-return.
- Runtime risks: createIntent builds the MIME filter from the input's accept list; some file managers grey out .zip/.csv they label application/octet-stream (the accept list also carries text/csv, application/zip, x-zip-compressed, vnd.ms-excel). DecompressionStream('deflate-raw') needs a WebView based on Chrome 103+; otherwise the app asks to unpack the ZIP. Content URIs are read by the WebView itself (allowContentAccess=false does not affect file inputs). Not compiled here.
