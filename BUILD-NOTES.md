## Bridge additions beyond the plan
scanAll(ms), stopScan(), getState(); night data rows are [t, rr, hr, n] (n = RR count in the packet; JS applies the stale-repeat rule only to n == 1, like live mode). startNight returns {"ok":false,"error":...} on failure. Extra events: scanState, night (started/stopped), warning (lowBattery), appResumed, error, permissions.
Night CSV has "#start", "#gap", "#end" comment lines (parsed by NightStore, skipped in getNightData).

## Design decisions
- Scan is unfiltered; callback keeps devices advertising 0x180D or named WHOOP*/Polar* (with ScanFilter alone a WHOOP not advertising the UUID would be missed).
- Wake alarm and "Zakończ" action go to WakeAlarmReceiver, which calls NightService.instance.requestStop() directly, or NightStore.finalizeOrphan() when the process/service is dead (no background FGS start needed). START_STICKY restart resumes the same file (append) from Prefs.
- No dynamic receivers, so ContextCompat.registerReceiver is not needed. All PendingIntents use FLAG_IMMUTABLE.
- Night below 6 valid windows is NOT saved automatically: card offers "Zapisz mimo to" / "Odrzuć".
- Blob downloads in the web UI (export JSON/CSV buttons) will not work in WebView (no DownloadListener). Not implemented.

## Bluetooth connection stability (reconnect, band priority, live service)
- BleManager.kt: link supervision. `wantConnected` (the user wants the link) + `targetAddress`; every unexpected loss goes through `handleLinkLoss(g, status)`: always `gatt.close()`, wait max(backoff, 600 ms for 133/8/19/22), retry. Backoff 2, 4, 8, 15, 30 s then every 30 s (mirror of `NATIVE_BACKOFF` / `nativeStep()` in execution/ble-core.js, covered by node tests). First connect and the first 3 retries use `connectGatt(ctx, false, cb, TRANSPORT_LE)`; from the 4th attempt `autoConnect = true` (no timeout, `autoTick` refreshes the attempt counter every 30 s). Repeated 133 (>= 2 in a row) calls the hidden `BluetoothGatt.refresh()` by reflection (try/catch Throwable) before closing. New state "reconnecting" (events carry attempt, reason, code), `reconnectAttempt` is reset on the first real HR notification, not on the CCCD write.
- After service discovery: `requestConnectionPriority` (HIGH while the web app says "session"/"diag" and no night is running, BALANCED otherwise / at night; `setLiveUse`, `setNightUse`), `requestMtu(185)` queued as a GATT op (result ignored, onMtuChanged -> opDone). Every reconnect builds a new gatt, so 0x2A37 and the battery characteristic are re-subscribed by `setupServices`. GATT op queue: 10 s per-op timeout (`opTimeoutRun`) so one lost callback cannot freeze it. Watchdog: connected but no HR notification for 15 s -> `handleLinkLoss(gatt, STALE)` (kind "stale" in the log).
- Connection log: ring buffer of 100 entries (`connected`, `disconnect`, `stale`, `attempt`, `user`) with status code, Polish reason, attempt; `FormaBridge.getConnectionLog()`. In memory only (lost on process death).
- Preferred band: `Prefs.preferredId/preferredName/setPreferred` (falls back to the last connected device for older installs). `BleManager.connect(id)` (picker) makes the device preferred; `connectPreferred()` / `FormaBridge.connectPreferred()` connects only to it, never scans, never touches another heart-rate device. getState carries preferredId/preferredName/attempt/reason/code.
- LiveService.kt (new, manifest entry, foregroundServiceType connectedDevice): "Forma - polaczono z opaska" notification, 4 h partial wake lock, START_NOT_STICKY. `FormaBridge.setLiveUse("session"|"diag"|other)`: session = service + HIGH priority, diag = HIGH only. `LiveService.stop()` never calls stopService (a stop right after startForegroundService would crash with "did not then call startForeground"): onStartCommand sees `running == false` and ends itself. MainActivity keeps the WebView running and the event listener registered while `LiveService.running` (otherwise HR events would be dropped with the screen off).
- NightService: `BleManager.setNightUse(true/false)`, `connectNow()` / `reconnectTick` use `connectPreferred()`; its own backoff only matters when BleManager has given up (`state == "disconnected"`).
- Compile-risk spots: (1) BleManager: `private val reconnectRun = Runnable { ... }` / `connectTimeout` with nested if/else as the last statement of a SAM lambda (Unit); `val dev: BluetoothDevice? = try { ... } catch (...) { null }`; `private set` on `@Volatile var lastStatus: Int?`; `synchronized(connLog) { for ... }`; `o.put("code", e.status ?: JSONObject.NULL)` (Any overload); `when (status)` with `const val` branches; `main.postDelayed({ ... }, 1500)` (existing pattern). (2) `refreshGatt`: `g.javaClass.getMethod("refresh")` hidden API, wrapped in catch Throwable. (3) `override fun onMtuChanged(g, mtu, status)` signature. (4) LiveService: unqualified STOP_FOREGROUND_REMOVE and START_NOT_STICKY, `companion object` with `@Volatile var`, `Handler(Looper.getMainLooper()).post { instance?.finishSelf() }`. (5) FormaBridge.getState/onState `BleManager.lastReason ?: JSONObject.NULL`. (6) Notifications.live uses the private `openApp` of the same object.
- Runtime risks (not compile): WHOOP in HR Broadcast mode accepts one connection, so the WHOOP app on the same phone can steal the link (the banner text says so); autoConnect = true depends on the band advertising with a stable address; `BluetoothGatt.refresh()` may be blocked on some Android builds; the 15 s watchdog also fires when the band is removed from the wrist and stops sending HR (it then reconnects every ~17-45 s, harmless); stale callbacks after an op timeout can complete the next op early; vendor battery savers can still kill LiveService/NightService.

5. Last resort (build green without Health Connect, web falls back to "dostepny w aplikacji na Androida" because `FormaNative.hcStatus` disappears): delete HealthConnectManager.kt and HealthPermissionsRationaleActivity.kt; in FormaBridge remove the `init { HealthConnectManager.emitter ... }` block and the five `hc*` methods; in MainActivity remove the PermissionController import, `hcLauncher`, `askHealthPermissions`, and the `HealthConnectManager.emitter = null` line; in the manifest remove the 15 `android.permission.health.*` lines, `<queries>`, the rationale activity and the alias; in app/build.gradle.kts remove the two dependencies. ### Bridge (all return JSON strings; results of long work arrive as events)
- `hcStatus()` -> `{ok, status: available|update|unavailable, sdk}` and event `hcStatus {status, sdk, granted[], missing[]}` (lists only when available).
- `hcRequestPermissions()` -> `{ok:true}` then event `hcPermissions {granted[], missing[]}`; when Health Connect is missing / too old: opens the Play Store page and returns `{ok:false, code:"unavailable"}`.
- `hcSync(sinceIso)` -> `{ok:true}` then event `hcSyncResult {ok, since, data{stepsDaily[{date,steps}], stepsHourly[{t,steps}], weight[{t,kg,origin}], height[{t,cm,origin}], exercise[{id,type,start,end,title,origin,hrAvg?,hrMax?}], sleep[{id,start,end,title,origin,stages[{s,e,st}]}], rhr[{t,bpm,origin}], hrv[{t,rmssd,origin}], calDaily[{date,active?,total?}]}, failed[], granted[]}` or `{ok:false, code, message}`. Times are epoch ms; only granted categories are read, a failing category goes to `failed` and does not lose the others. One sync at a time.
- `hcWrite(json)`, json = `{"records":[{kind: hrv|rhr|exercise|hr|sleep, cid, ver, off, ...}]}` -> `{ok:true}` then event `hcWriteResult {ok, written[cid], failed[{cid,error}], denied[kind]}`. Records go in per kind; a failed batch is retried record by record.
- `hcOpenSettings()` -> opens Health Connect settings (three known actions tried), Play Store page when Health Connect is missing.
- Extra event `hcError {code, message}` (used by the manager for permission read failures / Play Store failures).

### Behaviour
- Sync window (web decides): first sync 30 days, afterwards exactly last sync - 2 days; the manager clamps `since` to 30 days. Health Connect itself only returns data from before the permission was granted for 30 days unless READ_HEALTH_DATA_HISTORY is declared (not requested).
- Steps use `aggregateGroupByPeriod` (per local day) and `aggregateGroupByDuration` (per hour from local midnight), so overlapping data of several apps is de-duplicated by Health Connect.
- Records written: HRV (RMSSD) at the measurement time, resting HR, exercise sessions (STRENGTH_TRAINING / RUNNING / WALKING / OTHER_WORKOUT; sauna never), HeartRateRecord with samples every 5 s, sleep session without stages ("Sen (Forma)"). `Metadata(clientRecordId = our id, clientRecordVersion = write time in ms)`; the web ledger (`forma.v1.hc` -> `written`) rewrites a record only when its content changed, with a higher version.
- Never written back: workouts / weights / sleep that came from Health Connect or WHOOP (planner rule + test), records with our own origin are skipped on import (`pl.forma.app`), no second sleep session for a night another app already has, only records of the last 30 days.

### Runtime risks (not compile)
- The permission dialog only appears if Health Connect finds the rationale activity (declared) and the permissions in the manifest (declared). A user who denied twice gets no dialog again: the card's "Zarzadzaj uprawnieniami" opens the settings.
- Health Connect is Google's / Samsung's data store: apps like Samsung Health must be set to share into it; a watch that only syncs once a day gives yesterday's data.
- `aggregateGroupByDuration` over 31 days = 744 buckets (fine); hourly sums can differ by a few steps from the daily total (the web uses the daily value for the total and the hourly values only for the distribution).
- Exercise type numbers in the web label map (SPORT) and the stage codes (1 awake, 2 sleeping, 3 out of bed, 4 light, 5 deep, 6 REM, 7 awake in bed) are written from memory of the Health Connect constants; a wrong label would only be cosmetic, a wrong stage code would shift minutes between stages.
- Reads happen only while the app is in the foreground (no background-read permission); the first sync after the user grants permissions is limited by Health Connect to 30 days of past data.
